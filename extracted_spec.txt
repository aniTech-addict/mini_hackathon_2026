P10 – Post-Operative Recovery SystemComplete API Route Specification
Patient + Doctor | AI/OCR Discharge Processing | Recovery Plan | Calendar | Checklist | Alerts
This document defines the proposed backend API surface for the revised P10 implementation. The application has two roles only: Patient and Doctor. The main workflow is: Doctor uploads a discharge/recovery document → OCR/text extraction → AI contextual extraction → AI-generated recovery plan draft → Doctor review/approval → Patient daily calendar and checklist → Daily review and adherence → Alerts → Doctor monitoring.

14. Alert Generation Flow
Scheduled task      |      vStill pending after configured grace period?      |     YES      |      vCreate TASK_MISSED alert      |      +--> Patient alert      |      +--> If repeated / clinically relevant:                    |                    v              Doctor alert
The scheduler/alert engine should be an internal service or background job, not a public endpoint. Public APIs are used to read and manage alerts.
15. Authorization Rules
Only authenticated users can access protected endpoints.
Patient can access only their own patient data, active recovery plan, tasks, completion history, daily reviews, reports and alerts.
Patient cannot create, approve, or modify doctor-prescribed recovery plans/tasks.
Doctor can access only patients assigned to that doctor.
Doctor can upload/process reports for assigned patients.
Doctor can correct extracted report data and generate/edit/approve recovery plans.
A recovery plan should remain DRAFT until doctor approval.
Only an ACTIVE approved plan should drive the patient's daily calendar.
A patient must not be able to mark another patient's task as completed.
A doctor must not be able to resolve an alert belonging to an unrelated doctor's patient.

17. Recommended End-to-End Demo Test
1. Doctor logs in.2. Doctor selects Patient-001.3. Doctor uploads a handwritten discharge/recovery paper.4. Backend creates a medical_reports record.5. OCR extracts the handwritten content.6. AI converts the extracted content into structured medical context.7. Doctor opens extracted data and corrects anything necessary.8. Doctor triggers AI recovery-plan generation.9. AI creates a DRAFT recovery plan and tasks.10. Doctor reviews/edits the draft.11. Doctor approves the plan.12. Patient logs in.13. Patient sees Recovery Day 1 on the calendar.14. Patient sees prescribed tasks.15. Patient completes a task.16. Completion is stored in task_completions.17. A task is left pending/missed to test alert generation.18. Patient submits the daily review.19. Doctor dashboard shows adherence + daily review + alert.20. Doctor resolves the alert.
This demonstrates the complete P10 story: unstructured discharge information is converted into an actionable, doctor-approved recovery program and then monitored through daily patient activity.
18. Implementation Notes
Use multipart/form-data for report uploads.
OCR/AI processing should preferably be asynchronous for larger documents; return a processing/job identifier and expose status.
Store the original uploaded document and the normalized/extracted context separately.
Keep AI-generated recovery plans in DRAFT until doctor approval.
Treat AI output as a structured suggestion, not as an autonomous medical prescription.
Use transactions when approving a plan and activating its tasks.
Use authorization checks at the backend/service layer; frontend role checks alone are not sufficient.
Use synthetic data in development and testing environments.

Added Endpoint Details
1. Fetch Task by Task ID
GET /api/patient/tasks/:taskId
Authorization: Bearer {{patientToken}}
Purpose: Returns one recovery task belonging to the authenticated patient's active recovery plan. The response can include the task definition and the patient's scheduled completion status for the requested date/time when applicable.
Example response:
{  "task_id": "TASK-001",  "title": "Take prescribed medication",  "description": "Take medicine after breakfast",  "category": "MEDICATION",  "start_day": 1,  "end_day": 7,  "schedule_times": ["08:00", "20:00"],  "frequency": "DAILY",  "is_required": true}
2. Patient Creates an Alert
POST /api/patient/alerts
Authorization: Bearer {{patientToken}}
Purpose: Allows the patient to proactively report a recovery concern to the assigned doctor. The backend should associate the alert with the authenticated patient and, where applicable, the patient's assigned doctor.
Example request:
{  "type": "PATIENT_REPORTED",  "severity": "high",  "title": "Increased pain near wound",  "message": "Pain has increased significantly since this morning."}
Example response:
{  "id": "ALERT-001",  "patient_id": "PATIENT-001",  "doctor_id": "DOCTOR-001",  "type": "PATIENT_REPORTED",  "severity": "high",  "title": "Increased pain near wound",  "message": "Pain has increased significantly since this morning.",  "status": "unread",  "triggered_at": "2026-09-11T08:30:00Z"}
Authorization / Safety Notes for Added Endpoints
GET /api/patient/tasks/:taskId must return only a task that belongs to the authenticated patient's recovery plan.
POST /api/patient/alerts must derive patient_id from the authenticated session rather than accepting an arbitrary patient_id from the request body.
The backend should associate the alert with the patient's assigned doctor when one exists.
Patient-created alerts should be visible to the assigned doctor through the existing doctor alert endpoints.
Creating an alert does not replace emergency medical care; the application should provide an appropriate emergency-care message for critical situations.
